## Executive Summary

The single biggest finding: RBAC/identity is not a missing convenience feature — it's **actively broken in a privilege-escalation-class way**, and it structurally blocks role-native HUBs and the admin command center. `coerceRole()` (`src/types/subscription.ts`) silently promotes four DB-valid roles (admin/supervisor/accountant/stockkeeper) to `'owner'` in every client-side permission check. A production check run during this session confirms the honest urgency framing: **zero real tenant_users today hold those three affected roles** (only `owner`×6 and `admin`×4 — the latter being the KiTS-staff auto-injection, already correctly aliased). This is a landmine to defuse before real customers hit it, not something bleeding today — which is why, on the founder's explicit call, it still ships strictly first (security discipline over live-impact ranking), but the fake Call-Waiter/Fa7em buttons (which *do* affect real diners today, if any restaurant tenant is active) follow immediately after, not weeks later.

An adversarial second Opus pass materially reshaped the plan from its first draft — most importantly, it found that "Track 1" as one XL blocking unit was wrong-sized: only a narrow slice (`coerceRole` fix + a small `RoleRoute` component cloned from the existing `FeatureRoute.tsx` pattern + a single-function RLS alias extension) actually gates the role-HUB work; PIN login, the audit log, and employee↔tenant_user reconciliation have no technical dependency relationship to that and were needlessly blocking it. It also surfaced a live, already-shipped identity conflation (the "platform admin" hack) that the original draft would have folded into Track 1 by mistake, and found that the unit test suite currently *asserts the security bug as correct behavior* — a landmine for whoever does the fix.

Most encouragingly: most of what the founder feared was missing already exists and is well-built (3D floor plan is genuine WebGL/PBR, the login page is already polished — contrary to the founder's "bland" impression, most likely a stale-deploy/cache issue not a code issue, worth a live check — WaiterInterface/ArgileStation/KitchenDisplay/MultiBranchHub are all substantial). Most tracks below are wiring and consolidation, not from-scratch construction.

**1b — revised scope (2026-07-11), before any route was wired.** Attempting to wire `RoleRoute` against the legacy 4-role `UserRole` type surfaced that this was the wrong target: 3 of the 8 real DB roles (supervisor/accountant/stockkeeper) currently collapse into `viewer` via `coerceRole`, so route policy built on `UserRole` would be immediately too coarse. Founder-confirmed architecture, replacing the "consolidate onto one source" line above with a concrete decision:

- **The 8 canonical roles (`RoleType` — owner/admin/manager/supervisor/cashier/accountant/stockkeeper/viewer) become the real security backbone** — routing, RLS, and `canPerform` — replacing the legacy 4-role system everywhere, not patching around it.

An owner (or KiTS, pre-seeding sensible per-vertical defaults) creates a named custom role on top of one of the 8 bases, with permission tweaks. Routes gate on the coarse base role; in-page actions gate on the finer permission set.
- **Custom roles may base off all 8 canonical roles**, not just the current `manager | cashier | viewer` restriction — removes an artificial limit (e.g., a custom "Junior Accountant" based on `accountant` isn't buildable today).
- **KiTS pre-seeds suggested starter custom roles per vertical** (Waiter/Floor Manager/Argile Staff/Receptionist for restaurant; equivalents for pharmacy/supermarket), owner/manager customizes from there — same "we suggest, you customize" pattern as Track 9's SOPs.

**Track 1c: DONE in full (2026-07-11).** Real per-employee PIN sessions, not just client-side attribution. Founder explicitly rejected the industry-standard "terminal stays authenticated, PIN just attributes" model as too weak — wanted a genuine security boundary. Architecture (Option B of two considered): every PIN-holding employee gets a **real `auth.users` account** with a synthetic internal email (e.g. `pin-<uuid>@pin.kits.internal`), and their **PIN is the literal password**, verified through Supabase's native `signInWithPassword()` — no custom token-minting edge function needed (that was Option A, rejected for build complexity vs. Option B's use of Supabase's existing session/JWT/RLS pipeline as-is). Trade-off named explicitly: a 4-6 digit PIN is a weak password in isolation, mitigated by (a) Supabase's built-in rate-limiting on failed sign-in attempts, (b) a compromised PIN only ever grants that specific employee's already-scoped role — never more, and (c) this is a *stronger* boundary than the entire rest of the POS category (Toast/Square/Lightspeed all use the weaker attribution-only model), not a weaker one.

**What's built and deployed:**
- `create-pin-employee` edge function (deployed, v2) — owner/manager/admin-only, creates the synthetic-email `auth.users` account + `tenant_users` row + `employees` row (with `email` set to the synthetic address, so the client can call `signInWithPassword` without needing a separate lookup against the protected `auth.users` schema).
- `CreatePinEmployeeModal.tsx`, wired into `Employees.tsx` via a new "Add PIN staff" button — name, standard-or-custom role picker, PIN + confirm.
- `PinLockScreen.tsx` — mounted once near the top of `App.tsx`'s provider tree (not per-page, so it can't be bypassed by navigating elsewhere). Tap-your-tile roster (filtered to employees whose `email` ends in `@pin.kits.internal` — i.e., only PIN-capable accounts appear, legacy no-`user_id` employees don't) → PIN pad → `signInWithPassword()` swaps the real session. Auto-locks after 5 minutes of inactivity (mouse/keyboard/touch/scroll tracked); a "Switch User" button in `Layout.tsx`'s header (dispatches a `kits:lock-terminal` window event, handled via `src/utils/terminalLock.ts` to avoid a fast-refresh lint violation from co-exporting a function alongside the component) triggers an immediate manual lock.
- **Clock-in integration**: on successful PIN unlock, `clockInIfScheduled()` looks up today's `restaurant_shifts` for the tenant, finds a matching `restaurant_shift_assignments` row for that employee with `clocked_in_at IS NULL`, and sets it — mirrors the exact update `ShiftManager.tsx`'s own "clock in" button already performs, so both paths stay consistent. Best-effort: no shift scheduled today, already clocked in, or a non-restaurant tenant all silently no-op — clock-in is a bonus side effect of unlocking, never a blocker on login succeeding.
- **Audit log**: reused the existing platform-wide `activity_log` table (migration `000006`) rather than building a parallel one — it was already exactly the right shape (`tenant_id`, `user_id`, `action`, `entity_type`, `entity_id`, `metadata`) and already RLS-scoped correctly. `employee_pin_login`/`employee_pin_logout` events write on every PIN sign-in, on explicit "Sign out completely," and — critically — on every *session swap* (logs the outgoing PIN employee's logout using their about-to-be-replaced session, immediately before `signInWithPassword()` replaces it; there's no way to write "as" them afterward). Action names use the existing `employee_` prefix convention from `ActivityLog.tsx`'s `getCategoryFromAction()`, so entries surface correctly under the "employee" category with zero display-code changes needed — verified by reading that page's actual categorization/formatting logic and its main query (unfiltered beyond RLS), not assumed.
- Verified clean at every step: typecheck, full-project lint (zero warnings), full test suite (330 passing), production build.

**Scope note carried forward, not re-litigated:** this is the audit log's *plumbing* (real login/logout events, tied to a real per-employee identity) — it does not yet extend to logging every in-app *action* (sales, voids, edits, etc.), which would mean instrumenting call sites across the app. That's a natural, larger follow-on, not silently implied to be done by "the audit log is built."

**Known, accepted limitation:** the newly-created PIN employee won't appear in the lock-screen roster until `AppContext`'s employee list next refreshes (e.g. a page reload or tenant switch) — `AppContext` doesn't expose a public `reloadData()`/`refreshEmployees()` the modal could call after success. This matches the *existing* behavior of `InviteTeamMemberModal` (which has the same gap today), not a regression introduced by this feature — flagged, not fixed, consistent with today's scope discipline.

**Resolved flow design** (avoids needing any PIN-uniqueness constraint or a separate PIN→employee lookup table): the lock screen shows a **tap-your-name/tile roster** of employees (scheduled-today via `restaurant_shift_assignments`, or all active employees as a fallback) — tap a tile, a PIN pad appears, enter PIN, client calls `signInWithPassword(thatEmployee'sSyntheticEmail, enteredPIN)`. The employee is already identified by the tap, before the PIN is even entered — so PINs never need to be unique across a tenant, and there's no reverse-lookup problem. This is also a well-established real POS pattern (Toast/Clover show name/photo grids), not a novel invention.

**Resolved: clock-in bundling.** PIN-unlock doubles as clock-in, reusing the existing `restaurant_shifts`/`restaurant_shift_assignments` tables (Track R.5) rather than building new scheduling infrastructure.

**Session-swap behavior, named explicitly:** `signInWithPassword` replaces the current session in that browser tab/localStorage — whoever was previously active (e.g. the owner) is silently signed out of that specific terminal when an employee PINs in. This matches how physical POS terminals actually work (one active identity at a time) and is not a bug to engineer around.

**PIN-only v1 vs. PIN+QR-badge:** still open — QR-code badge (camera-only, zero hardware cost, Lightspeed/Clover/TouchBistro pattern) is the safer default over NFC (Square's pattern, requires an existing contactless reader) for Lebanon's uneven hardware ownership, but not needed for a v1 PIN-only build.

**Concrete build scope, not yet started:** (1) a new edge function (service-role, owner/manager-only) that creates the synthetic-email `auth.users` account + `tenant_users` row + `employees` row (with `user_id` populated — see Track 1d note below) given a name/role-or-custom-role/PIN; (2) a lock-screen overlay component (employee tile roster + PIN pad), likely at the `Layout.tsx` level so it can gate any authenticated route after an inactivity timeout or a manual "Switch User" trigger; (3) inactivity-timeout logic; (4) clock-in integration on successful PIN-unlock; (5) the audit log itself (login/logout/clock-in events at minimum, ideally extensible to action-level logging later) — genuinely new, no existing table for this beyond the platform-wide `activity_log` (migration `000006`), which could plausibly be reused rather than building a parallel table, worth confirming before implementation.

### Track 10 — Customer Service & Complaint Resolution
*Tier 2 · Effort M · builds on existing `restaurant_table_feedback`, no hard dependency*

`TableFeedback.tsx`/`restaurant_table_feedback` today is write-only from the customer's side — collects ratings/tags/comments with zero staff-facing follow-up. **Review-reward mechanism — redesigned from the original ask, founder-approved.** The original idea ("5-star Google review with photo → automatic free dessert") has two real problems, not one: Google's Business Profile API architecturally cannot identify *which specific customer* posted a given review — there's no workaround, it's a deliberate privacy boundary, not a missing feature. ### Track 13 — Music & Ambience Control
*Tier 3 · Effort L (real hardware product, not pure software) · Wave 3, deliberately sequenced late*

Real control of a venue's actual music/lighting from the app, not a manual checklist. Research ruled out the obvious paths: **consumer Spotify is a dead end regardless of licensing** — a Feb 2026 policy change caps unapproved third-party apps at 5 total authenticated users ever, with no realistic upgrade path for a company KiTS's size, and public playback of a personal Spotify/Apple Music account is a licensing violation independent of API access. **Sonos control is genuinely free to build against, but most Lebanese restaurants don't already own Sonos hardware** ($75–500+/speaker) — not a "control what they have" story for most of the target market.

**Recommended build — genuinely $0 for KiTS, fits the existing architecture**: a local Pi/ESP32 box (Mopidy or Music Assistant for audio, WLED for addressable lighting) that KiTS's cloud app talks to via **Supabase Realtime** — the same signaling-channel pattern already recommended for Track 4's remote support, no new infra. This is also the same category as the original "Local Hardware Interfacing" architectural principle (ESP32 for receipt printing/cash-drawer triggers) — build one general-purpose local KiTS hardware agent rather than a separate one-off per use case, so printing, cash-drawer, and ambience control all ride the same local-agent channel. Local-first also means playback/lighting control survives Lebanon's frequent power/internet outages, since commands only need the LAN.

**Honest framing**: this is effectively a small hardware product KiTS pre-builds and ships (a "KiTS Ambience Box"), not a pure software feature — real engineering + ongoing support burden (provisioning, offline resilience, hardware support), meaningfully different shape than every other track in this roadmap. That's why it's sequenced in Wave 3 alongside the 3D upgrade rather than with the rest — a deliberate founder decision, not a default. Hue (well-documented but requires real hardware spend most venues haven't made) and Sonos Pro/Soundtrack Your Brand (legitimate, licensed, API-accessible, but gated by partner approval and $29–54/zone/month) become optional premium integrations for the subset of venues that already run that gear, not the primary path.
